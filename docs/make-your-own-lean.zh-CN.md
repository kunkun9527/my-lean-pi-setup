# 自己动手做 lean 版

[English](make-your-own-lean.md) · [返回 README](../README.zh-CN.md)

原理和对比实例见文章[《省掉 91% 的工具提示词：给 Pi Agent 用户和扩展作者的操作指南》](https://zhuanlan.zhihu.com/p/2087689382069383746)。这里只放两段可以直接用的提示词：一段用来做，一段用来跟进上游。把 `<...>` 换成实际的包名，发给你的 agent 即可。

## 做法概要

新建一个包，把上游扩展装成依赖，外面套一层壳。上游注册工具时，这层壳先把工具拦下来，换上精简过的描述和 schema 再注册；真正执行时，还是调上游原来的代码。上游代码一行不复制，`node_modules` 也不动。

## 做一个 lean 版

```text
帮我给 Pi 扩展 <上游包名> 做一个 lean 版，包名叫 <上游包名>-lean。

目标：功能完全跟上游一样，只缩短模型每次请求都要读的工具描述和 schema。

做法：
1. 把上游装成依赖，锁定版本。不要复制上游代码，不要改 node_modules。
2. 先读上游，列出它注册的每个工具：description、promptSnippet、promptGuidelines、参数 schema，各占多少字符。
3. 用 Proxy 包住传给上游的 pi 对象，拦截 registerTool，把上游工具收集起来，换上精简版的描述和 schema 再注册。execute 直接调上游的。
4. 精简规则：
   - 同一件事只说一遍。
   - schema 已经表达的类型、枚举、长度、数量，不要再用文字写。
   - 删掉参数描述，字段名、类型和约束都保留；字段名看不出用途的，才留一句短描述。
   - 删掉只对人有用的界面说明。
   - 不用 MUST、NEVER、全大写这类语气。
   - 不要写死该由用户决定的事，比如"几步以上才用"。
   - 会影响模型怎么调用的规则要留下来。
5. 如果上游有多个工具，尤其是有很少用到的，合成一个工具：用 op 参数区分操作，常用参数放在 schema 里，冷门参数用 JSON 字符串传；加一个 op: help，返回上游对应工具的完整描述和参数。
6. 工具列表在会话中途不能变。如果上游会调用 setActiveTools，或者有"先调它再打开其他工具"的加载工具，都拦掉。
7. 模型常犯的调用错误，在校验前用代码补全，但只补不会猜错的情况；有歧义就返回清楚的错误。
8. 写测试：每个工具或 op 都能调到上游，help 能返回完整参数，补全逻辑不会误判，工具列表不会被中途改动。
9. 分别统计上游和 lean 版注册的工具占多少 token，写进 README。README 开头写明这是基于哪个项目、原作者是谁，并保留原来的许可证。
10. 写一份 MAINTENANCE.md，记下：对应的上游版本、每个工具精简了什么、依赖了上游哪些内部细节（工具名、校验顺序、加载工具等），以及升级步骤。

动手之前，先把上游工具清单和你打算怎么精简拿给我看。
```

最后那句"先拿给我看"很重要。哪些规则能删、哪些工具该合并，agent 有时会判断错，先看方案比做完再返工省事。

## 上游更新了，怎么跟

建议把上游版本锁死，每次手动升级。流程基本固定，也可以交给 agent：

```text
把 <lean 包名> 同步到上游 <上游包名> 的最新版。

1. 先读 MAINTENANCE.md，了解当前对应的上游版本和适配点。
2. 查上游最新版，对比两个版本的代码和 changelog，列出：新增或删除的工具、参数和默认值的变化、行为变化，以及 MAINTENANCE.md 里记的那些内部细节还成不成立。
3. 如果只是版本号变了、代码没变，直接升级依赖。
4. 有新参数或新工具的，按原来的精简规则加进 lean 版：常用的进 schema，冷门的放进 help。上游改了行为的，同步更新描述，不要让描述和行为对不上。
5. 跑测试，重新统计 token，更新 README 和 MAINTENANCE.md。
6. 把改动整理给我看，我确认后再发版。
```

上游大部分更新只改内部逻辑，升级依赖就完事；真要改适配代码的，一般是上游动了工具名或参数。
